## 范围与证据边界

本文将《分层任务协议方案》《分层任务协议详细设计》《测试计划与结果》与 Hark 对 a27a6d2 的复审发现映射为协议不变量及有限测试。Hark 报告只覆盖其列明的提交和复审范围；其中 CBC-01～06 有隔离缺陷复现，CBC-07、CBC-08、CBC-10 为静态推断，CBC-09、CBC-11 属分类或缓存边界。复审未覆盖的未提交工作树修改、后续维护结果及真实执行端行为均不由该报告证明。下文引用问题编号是历史证据索引，不表示这些问题在当前工作树中仍存在。

测试计划中的预期是实现门禁，不是现有代码行为。尚无明确命令或状态迁移的地方标为“设计缺口”；不能把 `recover`、`abandon` 或未来的资源解除接口解释成已经实现。

## 有限协议测试用例

所有用例使用临时状态根、固定时钟、合成 Hook/原生 transcript/Herdr 回执及故障注入；断言持久事件、状态投影、文件摘要和提交次数。不连接真实 Herdr、CBC 或通知 Relay，不消耗真实配额。每例检查唯一请求数、是否发生第二次输入、结果是否可重建及资源是否仍被隔离。

出口标记：`recover`、`rework`、`cancel`、`accept`、`status` 是设计中已出现的入口名，但具体参数和迁移仍以实现契约为准；`reconcile-admission`、`reconcile-stop`、`release-isolation`、`notification-reset` 是需要定义的接口名称，不表示已有 CLI。

|---|---|---|---|
| T01 正常闭环及逆序证据 | `request(q1,r0)` → `send-intent(q1)` → `Hook(UserPromptSubmit,session=s1,request=q1)` → `Stop(s1,q1)` 与 `delivery(q1,sha)` 分别先后交换到达 | 两种到达次序均只形成一次接纳；Stop 与结构化交付齐全后为 `review.pending`，产物 SHA 固定；不自动 accept。 | `status` → 主控 `accept`，或 `rework` 创建新 round/request；旧 round 不重开。 |

| T11 429/配额预算耗尽 | 同一 request 连续收到固定 N 次限流/配额拒绝，N 取配置上限；再到达一条迟到 ACK 和一条 duplicate 通知 ACK | N 次后显示确切 exhausted 原因，不产生第 N+1 次任务提交；迟到 ACK 只更新原 request，通知 ACK 不等于消费/accept。 | 额度恢复后通过显式继续原状态或新 attempt 关联处理；通知预算需 `[待定义] notification-reset`，必须限定到通知修订并留操作者/原因。 |
| T12 Pane/PID/watcher 编号复用 | q1 原 Pane/PID/watcher 退出；Herdr 将相同 Pane ID 或 PID 分配给无关进程/Pane；重启后 `task.watcherPid` 仍存旧值；执行 q1 recover/cancel/abandon | 单独相同编号不得证明原执行仍活，也不得证明已死；须比较 terminal/native session/出生时间或 watcher 实例证明。历史 review 与 q1 执行终态不因资源复用改写；不能误杀新进程/向新 Pane 输入。 | 精确证明旧 owner 已退出后允许 reattach 原观察或隔离关闭；若 worker 仍在，保持 held 并只附着观察。需要定义并测试 watcher 的正式认领/清理依据。 |
| T13 Stop Hook 上报失败 | 原生 Hook 已记录 `Stop(q1,s1)`；`report-agent` 超时；Herdr 仍为 `working`；注入原进程已空闲证明，再分别去除空闲证明 | 有精确 Stop 且空闲证据时，可收敛执行终态，观察健康另记 unavailable；不得因 Herdr 陈旧状态无限卡住或重投。没有空闲/原生终态证明时保持 unknown，不得猜完成。 | 有证据子例经 `recover`/`[待定义] reconcile-stop` 后可进 review.pending（仍须交付声明）；无证据子例只诊断、等待或隔离关闭。当前设计未定义如何补齐失败的 Herdr 状态。 |
| T14 Hook 截断、轮转与上限 | q1/q2 独立请求文件；q1 文件尾部半行后进程崩溃，再追加记录；同时轮转 q2 文件；另将单文件扩至上限以上 | 每个请求独立校验；截断/替换/缩小导致有界全量重读或仅该请求报错；上限按请求/证据窗口执行，q2 不被 q1 污染；不静默删掉审计证据。 | 请求级 `recover` 从保留原始记录重建；本轮证据已丢失时标记不可恢复并隔离，不影响其他请求。设计需补明确轮转和损坏文件保留规则。 |
| T15 等长原地改写及缓存失效 | 进程首次读取事件 A；同一路径原地写入字节数相等但内容不同的事件 B，并把时间戳设为相同粒度；再次查询 | 不得返回缓存 A 造成旧 round/旧 Stop 误判；内容摘要/版本证明失配时显式冲突或重新读取。 | 通过文件重读/摘要核对后 `recover`；无可靠版本证明时只拒绝该请求，不允许用缓存推断成功。 |
| T16 abandon 与隔离解除 | q1 为 submission_unknown、原生进程是否存活未知；执行隔离关闭；随后分别注入“原身份进程已退出+原会话无活动+写范围无 owner”完整证明及“只有 Pane 消失”弱证明 | 隔离关闭不写 cancelled/accepted、不释放资源；只有完整、精确证明才能将对应 resource 从 held/conflict 转 released；Pane 消失单证据不足。解除记录 actor/reason/evidence，并只释放本请求占用范围。 | 方案 R08 提出隔离关闭，但 `release-isolation` 尚未定义。缺命令、证明格式或窄范围规则即判设计未闭环；不得通过手工改状态模拟。 |
| T17 路径别名、双锁和慢外部调用 | 以同一 cwd 的真实路径与 symlink/junction 别名并发 acquire 同 request 锁；并行启动另一项目；第一进程持任务锁时让 Herdr/RPC 延迟 | 别名请求只能一个进入临界区；路径调度键与锁键一致；慢外部 RPC 不占用业务任务锁，独立项目可继续。无竞态写入/重复提交。 | 锁持有者仍有效则等待/报告冲突；陈旧 owner 需按实例证据回收后 `recover`。禁止按锁超时直接假定旧进程结束。 |
| T18 通知 ACK 丢失及预算耗尽 | `review.pending` 建立固定通知修订 → outbox 入队成功但 ACK 丢失 → 对账/重复投递 → 达重试上限 → 用户核验并重启该修订 | 业务任务始终只执行一次；queued、acknowledged、consumed、accept 各自可区分；预算耗尽可见；通知修复不改 review/执行历史。 | `recover`/通知对账只作用于原通知键；重置额度须 `[待定义] notification-reset` 并记审计，不接受重新 dispatch 作为通知恢复。 |
| T19 原生路径和时间戳兼容 | 配置 CBC 原生日志为非默认目录；再交换原生日志写入与 Hook 写入先后，保证二者具有同一原生消息/回合 ID | 若已配置受支持路径，应按稳定原生 ID 关联而不依赖粗粒度时间先后；未支持路径或缺少关联 ID 时明确拒绝并指向支持条件，不产生永久无诊断 unknown。 | 配置路径后 `recover` 重新读取原证据；若无法精确关联，隔离关闭。版本、默认路径与时间容差须形成显式兼容契约。 |

## 可能遗漏的永久卡住路径与闭环条件

1. **未关联 Hook 的未知提交没有有限出口。** `recover` 被定义为只读重建/恢复观察，而“Hook 无 `requestId/sessionId`”既不能接受也不能安全判未发送。当前方案允许无限停在 `unknown`；`abandon` 只能关闭协调，设计没有列出如何核实并释放已不再运行的资源。应定义证据字段、只读核验入口和带审计的资源解除出口。
2. **Stop 已落盘但 Herdr 仍 `working` 可永久等待。** CBC-08 指出 `wait_timeout=0` 可无限；设计将 observation 与 execution 分开，却未指定精确 Stop 与进程空闲证据如何修复观察投影。应测试有/无空闲证明两分支，并给有限等待后的隔离关闭策略。
3. **watcher/worker 的陈旧 PID 可能阻断所有恢复动作。** CBC-06/07 与 NEW-CORE-01 显示只凭 PID 或 Pane ID 可将复用资源当作原 owner；相反方向也不能因新 Pane 出现就判原任务 cancelled。需固定出生时间/实例身份字段及重启后 observer lease 的对账/回收规则。
4. **隔离关闭后资源永久锁死。** R08 提出隔离关闭，但缺少 `release-isolation` 的主体、权限/审核记录、证据类型、范围粒度和冲突重检。若任何一项无定义，abandon 后的 cwd/原生会话可能永久不能再派工；若只靠 `cancel` 解除，则 NEW-CORE-09 已展示弱证据旁路风险。
5. **Hook 证据仍可能形成状态根单点。** 设计说按 request 分文件，但需要明确 Hook 怎样在没有关联 ID 的情况下选择文件；同时要定义大小上限、轮转、尾部半行、损坏隔离和摘要重验。若仍全量扫描共享文件，会重现 CBC-02/03；若缓存仅用长度/mtime，会重现 CBC-11。
6. **请求未知状态的重试边界不完整。** “显式继续”适用于已证明未发送；“未知只对账”却没有对账失败后的终止/保留规则。必须区分 `not_sent`、`unknown`、`admitted` 并为每种状态指定唯一合法出口，不能以超时、429 或通知失败触发新 request。
7. **锁和路径别名缺少最终互斥证明。** 设计声明 realpath/内核锁与任务→请求锁序，但未覆盖 symlink/junction/subst、锁 owner PID 复用、协议版本遗留锁及慢 RPC 期间的跨项目进度。NEW-CORE-03/05/06 表明这些边界会造成重复写入或全局卡住。
8. **通知重试有界但耗尽后不可继续。** 设计有显式重启通知入口，尚未定义次数重置或审计；CORE-03/NEW-CORE-12 显示固定补送上限后可能永久静默。此路径应与任务重发完全隔离。
9. **管理/用户输入分类与安全门之间的竞态未覆盖。** CBC-01/05 证明同会话后续输入和 `/clear` 边界需按先后顺序处理；现有送前进程/租约/审批检查仍可能在检查与发送之间有原生输入。测试应注入“预检通过后、pane 写入前出现半行输入/审批状态变化”，预期明确拒绝或将提交标记 unknown，绝不能把消息落入审批框或新会话。

## 评审结论

方案的主要方向能表达请求身份、状态正交、事件幂等、未知不重发和交付冻结等安全约束，但还没有覆盖 Hook 关联标识缺失、真实资源身份复用、Stop 上报失败后的有限恢复、隔离释放及通知预算耗尽出口。上述 19 项用例可作为实现前的协议验收清单；在明确缺失接口并实现测试前，不足以据此判定方案闭环或实现完成。

## CBC V2 CLI 路由静态审查

审查范围：隔离 worktree 当前 `agent-bridge.js`、V2 协议实现、Hook 与调度模块；未修改运行源码，未连接 Herdr 或业务会话。以下运行观察来自主控提供的 R1/R2 测试结果，不代表本次重复执行。V2 入口 `bin/agent-bridge-v2.js:4-7` 只设置协议环境变量后复用通用 CLI，因此必须核对通用分支是否按持久化的 `taskProtocol` 路由。

**已核实的正向路径**

- R1 Hook 的 `promptSha256` 与 native transcript 精确指针摘要不同时，当前对账仍以唯一 native 指针、第一条原生输入及 Hook 先后关系建立接纳：`lib/cbc-protocol-v2.js:101-126`。主控报告 R1 recover 收敛到 `delivery_missing`，没有从文件存在推导交付；`sync` 将“执行已结束但没有冻结结果”投影为 `delivery_missing`：`lib/cbc-protocol-v2.js:181-190`。
- 新任务 Hook 忽略 `idle_prompt` 通知，权限通知仍留在处理集合：`hooks/cbc-task-events.js:16-18`；送前 Hook 边界校验也只排除 V2 的 `idle_prompt`：`lib/cbc-prompt.js:127-140`。主控报告首个 R2 的 guard 因 Stop 后的 `idle_prompt` 拒绝，精确过滤后保留 permission 检查。
- V2 `rework` 共用 `submit` 的前轮 Stop 预检调用 `cbc-turn.readTurn`，但该函数在读取旧 Hook journal 前先按 `taskProtocol===2` 转到 `cbc-protocol-v2.readTurn`：`bin/agent-bridge.js:221-224`、`lib/cbc-turn.js:264-265`、`lib/cbc-protocol-v2.js:161-169`。因此此前关于 V2 rework 仍读取旧 v1 journal 的缺口判断不成立。
- R2 延迟落盘根因已由主控补充：`UserPromptSubmit` Hook 先于 native transcript 行落盘，Hook capture 当时对账未能接纳；原 `waitForAgent` 只读投影，没有调用 `reconcileEvidence`，所以 20 s 等待超时。超时后 watcher 首次 reconcile 才建立 admitted，主控报告两者相隔 147 ms。当前 `waitForAgent` 在 V2 路径中每轮先本地调用 `reconcileEvidence`，native 行延迟出现时可在 UI 活性检查前补齐接纳：`bin/agent-bridge.js:79-90`。该路径只做本地证据对账；需用隔离测试确认 Hook 先到、native 行后到时不会再触发等待超时。
- V2 `resume`、`recoverOne`、`accept` 分别可路由到协议恢复、协议对账和冻结结果审查：`bin/agent-bridge.js:503-511, 566-568, 531-534`；accept 仅要求协议 review pending、control open，并校验冻结结果：`lib/cbc-protocol-v2.js:193-202`。这些分支没有重发任务或以当前资源状态改写冻结结果。

**待修复的路由与状态缺口**

1. **V2 不确定提交没有接入显式 transcript 对账入口。** `reconcile-submission --cbc-transcript` 仍未把 transcript 参数传入 V2 对账：`bin/agent-bridge.js:759-770`。CBC `submission.status==='observed'` 时调用 `cbc-turn.readTurn(task, { nativeTranscript })`，但该函数按 `taskProtocol===2` 转到 `cbc-protocol-v2.readTurn(task)`，没有转交 transcript 参数：`lib/cbc-turn.js:264-265`。`recoverOne` 对 V2 调用 `cbc-protocol-v2.recover(task)` 时也没有传入 transcript 选项：`bin/agent-bridge.js:566-568`；V2 recover 只按已保存的 Hook 路径对账：`lib/cbc-protocol-v2.js:105-115, 262-270`。Hook 证据缺路径或 transcript 后写入时，操作者没有明确 CLI 入口将精确 native 记录补交给 V2；unknown 可持续停留在观察/隔离状态。
2. **adopt-restored 会使后续 V2 Hook 与不可变 request 身份冲突。** 通用 `adopt-restored` 调用 `task-recovery.adoptRestored`：`bin/agent-bridge.js:712-715, 785-787`；`rebind` 会更新当前 `task.paneId/terminalId`：`lib/task-recovery.js:19-32, 49-54`。request 则冻结原 Pane/terminal：`lib/cbc-protocol-v2.js:54-62`，后续 `capture` 要求当前 task 身份仍与 request 原绑定相等：`:81-98`。原生 session 被合法移到新 Pane 后，后续 Stop/输入 Hook 将报 `Hook execution binding changed`，V2 观察无法收口。需把原执行身份与恢复后的观察定位分开，并记录可审计的恢复绑定。
3. **V2 abandon 状态不会落入 V2 请求日志，recover 可将其重新投影为活动任务。** CLI 使用通用 `coordination-exit.abandon`：`bin/agent-bridge.js:712-715`；该函数只把 task 文件改为 abandoned 并设置 resourceFence：`lib/coordination-exit.js:29-44`，没有追加 V2 `control.closed`/隔离事件。V2 `recover` 随后先 `sync` 再检查 abandoned：`lib/cbc-protocol-v2.js:262-270`；`sync` 根据 request log 的 control/review/execution 计算 task.status：`:176-199`。因此该操作可在恢复时被重写为 running、blocked 或 review_pending，resourceFence 也可能失去调度器识别所需的 abandoned 状态。V2 abandon 必须进入同一请求的持久终态或由恢复器显式保留隔离关闭。
4. **桥接指针之前出现人工输入会抛错但不形成明确冲突事件。** `reconcileEvidence` 找到精确指针后还要求它是本轮第一条原生用户输入、且 Hook 时间顺序一致：`lib/cbc-protocol-v2.js:105-126`。若同会话人工输入先于桥接指针，校验抛错；不会追加 `native.foreign_input`，recover 重试仍遇同一前置条件。安全结果是不误认接纳，但任务停在 unknown/error，缺少明确的人工输入冲突投影和正式恢复出口。相反，已确认 Stop 后的手工输入由 `capture` 的终态早退与独立 executor/UI 状态处理，不回退冻结结果：`:81-92`。
5. **调度路径别名仍按字符串路径比较。** `worker-scheduling.canonical` 使用 `path.resolve` 与大小写折叠：`lib/worker-scheduling.js:27-30`；资源冲突及同项目串行继续沿用该结果：`:39-49, 63-75`。同一目录的 symlink/junction 别名可形成不同键，可能绕过 V2 与其他任务之间的项目/写范围互斥。需将候选 cwd 与每个 write scope 规范到真实路径后比较。

主控提供的第二次 R2 实测记录为 admitted/running，但 CLI 曾报告等待 `working` 超时；测试配置下 watcher 到 180 s 时任务仍 running。根因时序是 Hook 先于 native 行落盘、capture 当时未接纳，而旧 `waitForAgent` 只读投影，没有触发 `reconcileEvidence`；watcher 首次 reconcile 才在 CLI 超时后建立 admitted（主控报告相隔 147 ms）。当前源码已在 `waitForAgent` 循环中加入本地 `reconcileEvidence`，与旧 v1 completion_seq 门禁不是同一根因；当前修改尚需隔离回归测试验证。本次静态审查未修改运行源码。

## 发布候选处置结论

上文为设计期间的缺口记录，不能直接作为当前未修清单。当前处置如下：V2 reconcile-submission路由至正式recover并使用绑定Hook的原生路径；不接受任意外部transcript补造归属。adopt-restored对V2在任何写入前明确拒绝，冷恢复仅用于已闭合协调后的新请求。abandon追加control.abandoned，后续恢复不能复活；调度路径和锁按真实路径处理别名。

Hook按请求日志保存，当前执行端用独立有界证据，不再依赖全局Hook日志。延迟原生记录通过本地reconcile补齐；重复、时间乱序、坏文件和通知失败已补回归。原生指针前出现其他输入时明确拒绝并保留诊断，不将错误终态强制认作本请求完成。

限制保留：没有通用的后台作业隔离自动释放协议；资源未知时保持隔离，必须以独立的新证据处理。原生Stop丢失不能仅凭idle补造。队列提醒预算耗尽后可用notifications pending主动取回并ack，不能承诺无限自动唤醒。TUI检查到发送之间仍有不可原子化的竞态。上述限制属于保守边界，并非已实现自动恢复能力。
